Toshiba eStudio printers and Gmail SMTP relays

January 4, 2018 3-minute read
Technology

I had an interesting issue today with Toshiba printers and Gmail SMTP relays.

Our church just recently switched internet service providers (ISPs). The migration was smooth and we didn’t encounter any issues. A shoutout to the Chorus technician who, despite his busy schedule and a foulup on a party’s side, came over on a Sunday to perform the switchover. Within a space of 1 hour, he reprogrammed the ONT and ensured connectivity to the internet.

3 days later, I received a phone call from one of the church staff stating that scan to email wasn’t working. I immediately suspected that the current SMTP settings on the Toshiba eStudio printer was set to our previous ISP. ISPs usually control their SMTP relays to only accept requests from their own networks to control spam outflow - I know I would do this if I were a network engineer in charge of a mail server.

I came in the next day to have a look at the printer settings, and sure enough, the settings were on the previous ISP. As we had an existing voicemail server using Gmail to send voicemail messages via email, I decided to set up the printer’s SMTP client to use that. The previous setting was on port 25; Gmail uses TLS on port 587 and SSL on port 465.

The problem came after the setup - no matter what setting was used, the printer simply refused to connect via TLS or SSL to Gmail. The error message “Unable to authenticate to mail server” came up each time an attempt was made.

Not to be outdone by a printer, I decided to setup a SMTP relay within the premises to help relay email messages from any SMTP client. It would serve only the local network - nothing more. There is already a Raspberry Pi in the server room running Debian that performs dynamic DNS updates and it seemed appropriate to give it something else to do other than that.

I installed postfix and libsasl-modules on the Pi.

sudo apt-get update && apt-get install postfix libsasl-modules

Mapping the Gmail username and password was the next step.

sudo cat /etc/postfix/sasl/sasl_passwd
[smtp.gmail.com]:587 gmail_username:gmail_password
sudo postmap /etc/postfix/sasl_passwd

I then added the additional configuration lines to /etc/postfix/main.cf. Note that this is assuming that when postfix was first configured, it was set to Internet Site.

relayhost = [smtp.gmail.com]:587
smtp_use_tls = yes
smtp_sasl_auth_enable = yes
smtp_sasl_password_maps = hash:/etc/postfix/sasl/sasl_passwd
smtp_sasl_mechanism_filter = plain
smtp_sasl_security_options = noanonymous
smtp_sasl_tls_security_options = noanonymous
smtp_tls_CAfile = /etc/ssl/certs/ca-certificates.crt
smtp_tls_note_starttls_offer = yes

After that, it was a simple case of restarting the postfix service

service postfix restart

To test the SMTP relay, I created a text file with the following contents

cat ~/test.file
From: xxx@gmail.com
To : xxx@yahoo.com
Subject : Test file
This is a test.
.

and issued the command sendmail xxx@yahoo.com < ~/test.file and voila! An email notification with the subject ‘Test file’ appeared in my inbox.

The advantage of using this approach is that this SMTP relay can be used in future by any device that performs email notification but cannot do SSL or TLS SMTP authentication. For example, this can be used by alarm panels, security cameras and NAS systems that exist in the same network as the SMTP server.
